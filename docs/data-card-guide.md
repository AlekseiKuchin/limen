# Карточка выгрузки

Карточка описывает одну выгрузку закрытых алертов: откуда она, что в ней, как определён источник закрытия и что известно о её недостатках. Заполняется до расчёта, хранится вместе с протоколом пилота у заказчика. Без карточки результат аудита нельзя правильно прочитать через полгода.

## Как заполнять

- Писать только то, что проверено: по документации системы, по самой выгрузке или со слов ответственного сотрудника заказчика — и указывать, откуда сведения.
- Неизвестное так и помечать: «не известно», «уточнить у …».
- Числа брать из вывода `limen validate`, а не считать вручную.
- Не вписывать в карточку значения из выгрузки: логины, имена хостов, адреса, тексты алертов.

## Шаблон

```markdown
# Карточка выгрузки: <заказчик>, <период>

## Источник
- Система и версия: <SIEM / SOAR, версия>
- Способ выгрузки: <REST API, отчёт, выгрузка из БД>; кто выгружал, когда
- Период: <с ... по ...>, часовой пояс в выгрузке: <...>
- Фильтры при выгрузке: <статус closed; клиенты MSSP; исключения>
- Маппинг: configs/mappings/<файл>.yaml, контрольная сумма: <sha256>

## Объём (из limen validate)
- Строк: <...>; повторяющихся alert_id: <...>
- По источнику закрытия: auto <...>, suppression <...>, analyst <...>, unknown <...>
- Правил корреляции: <...>
- Атак, найденных аналитиками (A_O): <...>

## Как определён источник закрытия
- Поле выгрузки: <...>
- Значения, означающие автозакрытие: <сервисная учётная запись SOAR, плейбуки, модуль ИИ>
- Значения, означающие подавление: <...>
- Чем подтверждено: <документация, ответ администратора SOAR, ручная проверка N алертов>
- Известные неоднозначности: <...>

## Вердикты аналитиков
- Поле и значения: <...> → attack / benign / unknown
- Насколько полно ставятся вердикты при ручном закрытии: <...>

## Оценка модели (score)
- Есть ли, откуда, шкала: <...>; приведена к 0..1: да / нет

## Обезличивание
- Поля сущностей и префиксы псевдонимов: <user → user, host → host, ...>
- Где хранится ключ, кто отвечает: <...>
- Создавалась ли таблица соответствия и где она: <...>

## Известные недостатки
- <пропуски, дубли, смена правил в течение периода, перерывы в выгрузке>

## Ограничения использования
- Для чего выгрузка может использоваться: <только этот аудит>
- Срок хранения у исполнителя и дата удаления: <...>
```

## Пример: синтетическая выгрузка для демо

Заполнен по генератору `src/limen/synthetic.py` с параметрами по умолчанию.

```markdown
# Карточка выгрузки: синтетика «Лимен», сентябрь 2026

## Источник
- Система и версия: генератор limen.synthetic (версия пакета 0.2.0), зерно 7
- Способ выгрузки: scripts/make_synthetic_export.py
- Период: 30 суток с 01.09.2026, время в UTC
- Фильтры при выгрузке: нет
- Маппинг: configs/mappings/generic_csv.yaml

## Объём
- Строк: 20 000; правил: 40; клиентов MSSP: 5
- Точные числа по источникам закрытия и A_O — из вывода limen validate

## Как определён источник закрытия
- Поле closed_by: playbook и ml_autoclose → auto, suppression → suppression, analyst → analyst
- Автозакрытие включено примерно в 60% правил; в них закрываются алерты с оценкой ниже 85-го процентиля
  оценок по всей выгрузке; в трёх правилах доля атак завышена до 3–8%, чтобы аудит находил «протекающие» правила

## Вердикты аналитиков
- Поле resolution: true_positive → attack; false_positive, benign_positive → benign; у автозакрытых пусто

## Оценка модели (score)
- Поле vendor_score, шкала 0..1, связана с атакой с шумом

## Обезличивание
- user → user, host → host, src_ip → ip; ключ secrets/demo.key создаёт make demo

## Известные недостатки
- Данные полностью выдуманы и не описывают ни одного реального SOC

## Ограничения использования
- Только демо и тесты
```
