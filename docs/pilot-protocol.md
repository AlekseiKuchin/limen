# Протокол пилота

Порядок аудита автозакрытия в действующем SOC: что фиксируется заранее, кто что делает, когда работа останавливается и что измеряется. Шаблон для заполнения — в конце документа.

## Участники

| Роль | Сторона | Что делает |
|---|---|---|
| Руководитель SOC | заказчик | утверждает параметры, принимает решения по итогам |
| Аналитики (1–3) | заказчик | перепроверяют отобранные алерты |
| Специалист ИБ или ИТ | заказчик | выгружает данные, хранит ключ обезличивания, согласует запуск «Лимен» |
| Исполнитель | «Лимен» | готовит конфигурацию, считает границы, разбирает отчёт с заказчиком |

## 0. Допуск

- Письменное согласие заказчика на пилот и на обработку выгрузки; соглашение о конфиденциальности.
- Режим поставки выбирается до выгрузки: основной, строгий или партнёрский (см. [README](../README.md#режимы-поставки)).
- Ответственный за ключ обезличивания назначается со стороны заказчика.
- Если заказчик — работодатель исполнителя, работа над «Лимен» и использование данных согласуются отдельно и письменно ([законы](compliance/law.md)).

## 1. Параметры фиксируются до выгрузки

Зерно, бюджет и схема выборки записываются в протокол до того, как кто-либо увидит данные. Тогда план нельзя подогнать под желаемый результат, а любая сторона может пересобрать его из выгрузки и конфигурации и сверить с исходным.

1. Скопировать `configs/audit.example.yaml` в файл пилота и заполнить: период, источники закрытия под аудитом, уверенность, порог `target_for`, бюджет, схему, зерно, политику «не знаю», поправку на число правил.
2. Период выбрать в пределах срока хранения событий в SIEM и EDR: аналитик должен иметь возможность разобрать каждый отобранный алерт.
3. Записать в протокол SHA-256 параметров: `limen config-hash pilot.yaml`. Тот же хеш `limen plan` запишет в план выборки, и `limen estimate` остановится, если параметры потом изменятся. SHA-256 таблицы алертов печатает `limen plan` (шаг 5) — его тоже записать.

Для выводов по пилоту используется схема `uniform`: схема `active` пока даёт только приближённую границу ([methodology.md](methodology.md)).

## 2. Выгрузка

| Поле | Зачем | Если нет |
|---|---|---|
| Идентификатор алерта | связь плана и меток | аудит невозможен |
| Правило корреляции | границы и решения по правилам | только общий итог |
| Признак того, кто закрыл алерт | отличить автозакрытие от ручного | аудит невозможен |
| Вердикт аналитика для ручных закрытий | число найденных атак A_O, граница FNR | только граница доли атак |
| Время закрытия | проверка периода, мониторинг | без проверки периода |
| Причина закрытия | контекст для аналитика | — |
| Оценка модели вендора (score) | схема `active` | только `uniform` и `stratified` |
| Учётки, хосты, адреса | контекст; обезличиваются | — |

Признак источника закрытия обычно выводится из сервисной учётной записи SOAR, имени плейбука, модуля ИИ или правила подавления. Причины закрытия сами по себе его могут не давать: например, в KUMA их три («responded», «incorrect data», «incorrect correlation rule»), и по ним автоматическое закрытие не отличить от ручного. Подавленные события попадают в аудит, только если система создаёт по ним закрытые алерты.

Поля выгрузки описываются в маппинге (`configs/mappings/`) и в карточке выгрузки ([data-card-guide.md](data-card-guide.md)).

## 3. Проверка выгрузки

```bash
limen validate export.csv --mapping configs/mappings/<маппинг>.yaml --config pilot.yaml
```

Работа останавливается, если:

- источник закрытия неизвестен у всех алертов;
- среди алертов нет закрытых автоматически или подавлением.

Предупреждения записываются в протокол: нет вердиктов у ручных закрытий (граница FNR не считается), аналитики не нашли атак за период (граница FNR неинформативна), дубли `alert_id`, доля алертов с неизвестным источником закрытия.

## 4. Подготовка и обезличивание — в контуре заказчика

```bash
limen keygen --out secrets/pseudo.key
limen prepare export.csv --mapping ... --key secrets/pseudo.key --config pilot.yaml \
    --out data/interim/alerts.csv --audit-log reports/limen-audit.jsonl
```

Ключ остаётся у заказчика. Таблица соответствия псевдонимов (`--mapping-table-out`) создаётся, только если она нужна, и не покидает контур.

## 5. План выборки и шаблон разметки

Строгий режим — всё у заказчика:

```bash
limen plan data/interim/alerts.csv --config pilot.yaml --out plan.csv \
    --template-out labels_template.csv --page-out labeling.html
```

Основной режим — наружу уходит только минимальная таблица:

```bash
limen export-minimal data/interim/alerts.csv --key secrets/pseudo.key --out outbox/minimal.csv
# исполнитель строит план и шаблон по minimal.csv и возвращает шаблон
limen translate-ids labels_template.csv --alerts data/interim/alerts.csv --to original --out labels_local.csv
limen labeling-page labels_local.csv --out labeling.html
```

Проверка: при `uniform` и `stratified` отобрано ровно столько алертов, сколько указано в бюджете.

## 6. Перепроверка

Инструкция для аналитиков:

- разбирать алерт так же, как на обычном дежурстве, с доступом к SIEM, EDR и другим источникам;
- ставить один из трёх вердиктов: «атака», «не атака», «не знаю»; «не знаю» при расчёте считается атакой;
- разметить все отобранные алерты: заменять «неудобные» другими нельзя;
- если алерт не разобрать (например, события уже удалены), ставить «не знаю» и пояснять в комментарии;
- найденную атаку сразу передавать по процессу реагирования заказчика — аудит её не ждёт;
- если найденная атака относится к известной технике MITRE ATT&CK, указывать её (например, T1078 или T1059.001) — отчёт покажет, какие техники автоматика закрывает без человека.

Разметка идёт на офлайн-странице `labeling.html`: её открывают в браузере на рабочем месте аналитика, сеть ей не нужна. Страница сама считает время на алерт, сохраняет прогресс в браузере и выгружает метки кнопкой «Скачать метки (CSV)»; продолжить можно из ранее скачанного файла. После выгрузки меток данные страницы в браузере стоит очистить. Разметка в Excel или задачах SOAR тоже возможна: шаблон `labels_template.csv` защищён от формульных инъекций, время на алерт заполняется в `seconds_spent`.

Рекомендуется, чтобы второй аналитик независимо разметил случайную часть выборки, например 10%: расхождения покажут, насколько надёжны метки. В версии 0.2 это делается вручную.

В основном режиме размеченный файл переводится обратно в псевдонимы и передаётся исполнителю:

```bash
limen translate-ids labels.csv --alerts data/interim/alerts.csv --to pseudonym --out outbox/labels.csv
```

## 7. Расчёт и отчёт

```bash
limen estimate <alerts> --plan plan.csv --labels labels.csv --config pilot.yaml --out result.json \
    --audit-log reports/limen-audit.jsonl
limen verify result.json --alerts <alerts> --plan plan.csv --labels labels.csv --config pilot.yaml
limen report result.json --format html --out report.html
```

`estimate` остановится с кодом 3, если таблица алертов или параметры аудита отличаются от зафиксированных в плане. `verify` выполняет заказчик (в основном режиме — по своей копии минимальной таблицы): он сверяет SHA-256 входов и заново считает границы. Расхождение — повод остановить пилот и разобраться.

Отчёт разбирается с руководителем SOC: правила с решением «теряет атаки», правила с выводом «неясно» или «мало данных» и размер добора, техники ATT&CK у найденных атак, предупреждения проверки выгрузки.

Для мониторинга между аудитами итоги можно выгрузить в Prometheus: `limen metrics result.json --out <каталог textfile collector>/limen.prom` ([deploy/monitoring](../deploy/monitoring/README.md)).

## 8. Что измеряется

- время от получения выгрузки до отчёта, рабочих дней;
- медианное время перепроверки одного алерта;
- доля размеченных алертов и доля ответов «не знаю»;
- число атак, найденных среди автозакрытых;
- границы доли атак и FNR по потоку, число правил с каждым решением;
- решения, принятые заказчиком по итогам: какие правила или настройки автозакрытия изменены.

## 9. Завершение

- В основном режиме исполнитель удаляет полученные файлы в согласованный срок и письменно это подтверждает.
- У заказчика остаются ключ, план, метки, результат и отчёт.
- Итоги оформляются кратким актом с заполненным протоколом.
